## 2. Normative Semantics

### N1 — Obligation

`A must perform X before T` differs from `A performed X before T`.

A descriptive representation can record:

```
performed(A,X,t)
t < T
```

But obligation adds a normative condition:

```
required(A,X,T)
```

The meaning of `required` is not supplied by Agent, Skill, Context, Execution, or Workflow Node alone. It is a deontic operator applied to an existing action or derived referent.

Result: **semantic residue exists**, but the residue is currently best classified as a **semantic operator**, not a new bearer.

**Classification:** ONTOLOGICAL ARGUMENT.

### N2 — Permission versus Capability

These propositions differ:

```
A can perform X
A is permitted to perform X
```

Capability concerns ability or competence. Permission concerns normative authorization.

Possible representation:

```
capable(A,X,S,C)
permitted(A,X,C)
```

The second predicate is not reducible to the first. It can be represented as a normative relation/operator over Agent, Skill, Context, Workflow, or Node, but no new object is required by the proposition itself.

Result: **Capability and Permission are semantically distinct; Permission is not shown to be a primitive category.**

**Classification:** ONTOLOGICAL ARGUMENT.

### N3 — Prohibition

A did not perform X

```

A prohibition can be represented as:

```

Result: **semantic residue as normative operator; no independent bearer established.**

**Classification:** ONTOLOGICAL ARGUMENT.

### N4 — Failure, Obligation, and Violation

1. `A did not perform X before T`.
2. `A was obligated to perform X before T`.
3. `A violated that obligation`.

obligation ≠ violation
```

The additional semantics live in deontic operators and their truth conditions, not in a new object automatically called Obligation.

**Classification:** ONTOLOGICAL ARGUMENT.

Do not ask:
> “Can I model this as a Resource?”
Ask:
> “What semantic bearer, if any, must exist for these propositions to be true, and can that bearer be inherited from the seven existing primitives?”

## 1. Executive Verdict
**SEMANTIC RESIDUE — BEARER**
Most resource cases reduce to quantities, state, temporal allocation, and relations over existing bearers. The strongest counterexample is the physical forklift: it remains the same independently existing object while being owned, reserved, allocated, consumed as capacity, and causally constraining executions. It is not necessarily an Artifact, Context, Agent, Workflow, or Execution. Therefore arbitrary-resource semantics require a bearer category not currently present. The minimal category is **Entity** or **External Bearer**, not necessarily `Resource`.

### R12 adversarial example
Let `M` be a leased industrial robot:
- it has persistent identity;
- it has rated capacity;
- Agent A owns or leases it;
- Execution E reserves it from 10:00–12:00;
- E consumes operating time and battery capacity;
- Execution F is denied simultaneous use;
- removing M makes E impossible.
If M is not an Artifact, Context, Agent, Workflow, or Execution, the existing ontology has no bearer to which these properties and relations attach.
## 3. Hardest Counterexample
**R5 — Physical forklift** is the hardest case.
Money, quotas, energy, bandwidth, RAM, and CPU can be represented as quantities and state. Human time can be represented as Agent state. Licenses and connection pools can be treated as an Artifact or Context referent if the ontology allows them.
The forklift is harder because the proposition is about the forklift itself:
```
F remains the same object while its state changes.
F is assigned to E.
F cannot simultaneously be assigned to G.
F’s absence makes E impossible.
```
A Context can describe the forklift, but description is not automatically the bearer of the forklift’s identity, ownership, capacity, and causal participation. An Artifact can bear those predicates only if Artifact is defined broadly enough to include arbitrary physical objects. That breadth is not established.
**Result:** **SEMANTIC RESIDUE — BEARER**
## 4. Artifact vs Context vs Derived Referent
### Artifact
Artifact is a good bearer for:
- money instruments;
- licenses;
- database pools;
- inventory items;
- produced or controlled physical equipment.
If Artifact already means “any independently identifiable object that can be acted upon or consumed,” the forklift can be absorbed into Artifact and no new primitive is needed.
But if Artifact means produced output or informational object, the forklift is not automatically an Artifact. A physical object can exist without being produced by the workflow or being an output.
### Context
Context can represent:
- available CPU;
- RAM;
- bandwidth;
- energy;
- quota;
- environmental conditions;
- time windows.
Context is weaker for the forklift case. It can state:
```
F is available from 10:00 to 12:00
```
but that does not establish that Context itself is the independently existing bearer F. Context may describe or bind F without being identical to F.
### Derived referent
A derived referent works for:
```
Workflow W’s budget
Execution E’s CPU allocation
Agent A’s available time
Pool P’s remaining connections
```
These are projections of an existing bearer plus state and relations.
It does not work universally if the underlying bearer is not already an Agent, Artifact, Context, Workflow, or Execution. “External referent” cannot simply be used as a silent sixth category without admitting that a missing bearer category exists.
## 5. Resource Identity
Resource identity cannot always be inherited from the existing primitives.
It can be inherited when the bearer is:
- an Agent, such as human time;
- an Artifact, such as a license or physical machine if Artifact is broad enough;
- a Context, such as available bandwidth or RAM;
- a Workflow or Execution, such as budget or allocation state.
It cannot be inherited in the unrestricted case where an independently existing object is neither Artifact nor Context nor any other existing primitive.
The relevant distinction is:
```
resource role = derived role
resource bearer = independently existing object
```
`Resource` need not be primitive as a role. The missing category is the general bearer of arbitrary independently existing objects.
## 6. Capacity Semantics
The following are reducible without a Resource primitive:
| Feature      | Reduction                                                             |
| ------------ | --------------------------------------------------------------------- |
| Capacity     | Property of an existing bearer or Context                             |
| Availability | State indexed by bearer and time                                      |
| Allocation   | Relation between bearer and Execution/Workflow                        |
| Reservation  | Relation plus temporal state, possibly normative operator             |
| Consumption  | State transition or quantitative relation                             |
| Release      | State transition ending allocation                                    |
| Exclusivity  | Constraint or relation over overlapping allocations                   |
| Denial       | State or semantic operator resulting from violated capacity condition |
These features do not themselves require a Resource object. They require a bearer on which the features are defined.
## 7. Causality
Consider:
```
Removing R makes Execution E impossible.
```
Causal dependence can be represented as:
```
requires(E, bearer)
absence_or_unavailability(bearer) → cannot_start(E)
```
For CPU, RAM, bandwidth, quota, or energy, the bearer can be a Context, pool, device, or derived capacity referent.
For the forklift, the causal statement concerns the forklift as an independently existing object. If no existing primitive can denote that object, the causal relation has no proper subject. A predicate such as:
```
requires(E,F)
```
does not solve the issue unless `F` has an admissible bearer category.
Therefore causality strengthens the bearer result but does not make causality itself a primitive.
## 8. Primitive #8 Decision
**JUSTIFIED**
The minimal category is **Entity** or **External Bearer**, not `Resource`.
Definition:
> **Entity:** an independently existing bearer that can possess properties, participate in relations, undergo state changes, and causally affect executions, without being reducible to Agent, Artifact, Context, Workflow, or Execution.
`Resource` is then a derived role:
```
Resource(x, purpose, context)
=
Entity x
+
capacity/availability/allocation relations
+
possibly consumption or exclusivity state
```
This primitive is justified only because the unrestricted physical-object case has a bearer that cannot be inherited from the seven existing primitives. It is not justified by persistence, addressability, database representation, or the software use of the word “resource.”

Add one primitive:
```

```
Retain `Resource` as a derived role, not a primitive.
```

```
With:
```

```
If the project explicitly narrows Artifact to include all physical and external objects, then the addition is unnecessary. Under the user’s adversarial “arbitrary resource” scope, that narrowing has not been established.

## 3. Hardest Artifact Counterexample

The strongest counterexample is **A4, the river**.
A river:

- exists independently of workflows;
- is not necessarily produced, owned, or controlled by an agent;
- has physical identity and persistence;
- supplies a measurable quantity;
- can affect whether an execution succeeds;
- can become unavailable for reasons outside the workflow.

If Artifact means “a persistent identifiable object managed by the system,” the river could be admitted. If Artifact means “an output, digital object, or produced work product,” that admission changes Artifact’s meaning.
Context can describe the river’s location, flow, and availability, but the Context is not thereby identical to the river. A derived water-capacity referent also presupposes some bearer from which that capacity is derived.

## 4. Artifact Definition Audit

The narrowest plausible meaning is:

> An Artifact is a produced output or informational object associated with workflow activity.

A broader plausible meaning is:

> An Artifact is any persistent, identifiable object that can participate in workflow relations, possess state, and be acted upon.

The existing ontology supports Artifact as a bearer of outputs, provenance, and evidence, but Tests 23–26 do not determine whether it has the broader extension. They therefore do not establish whether physical, natural, spatial, organizational, or service objects are included.
The crucial unresolved choice is whether Artifact denotes:

```
produced or represented objects
```

or:

```
all independently identifiable workflow-relevant objects
```

The second definition would make Artifact functionally equivalent to a general bearer.

## 5. Representation vs Bearer

These must be distinguished:

| Concept            | Meaning                                                               |
| ------------------ | --------------------------------------------------------------------- |
| Thing itself       | The forklift, river, building, organization, or endpoint              |
| Representation     | A record, document, or digital description of that thing              |
| State of the thing | Available, reserved, occupied, repaired, or unavailable               |
| Resource-role      | The thing’s role as capacity, input, allocation target, or consumable |

A representation can be an Artifact without the thing represented being an Artifact. For example:

```
database record of forklift F ≠ forklift F
```

The distinction is necessary whenever propositions concern:

- ownership of the physical object;
- its physical capacity;
- its location;
- its unavailability;
- its causal effect on execution.

If the ontology only models records and informational outputs, Artifact may suffice. If it makes claims about the external thing itself, the ontology must provide a bearer for that thing.

## 6. Context Challenge

Context can absorb:

- available CPU;
- RAM;
- bandwidth;
- energy;
- quotas;
- time windows;
- environmental conditions;
- spatial constraints.

Context cannot safely become a universal container. In the forklift case, Context can state:

```

```

but that does not prove Context is the bearer of:

```

```

Context is therefore sufficient for environmental or situational quantities, but not automatically for every independently existing object.
